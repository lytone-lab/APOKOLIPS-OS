  [ ] Window glass V2 — real glass (real backdrop, not wallpaper)
      Currently the app header strip shows a *blurred wallpaper*
      behind the traffic lights. Real macOS glass blurs what is
      actually behind the window — other windows, desktop icons,
      the dock. On Wayland apps cannot read pixels behind them
      directly, so the only path is:
        1. Shell captures the screen (grim) around the window's
           rect when the window moves, resizes, or a window
           beneath it changes.
        2. Shell writes the cropped region to a shared file or
           socket keyed by the app's sway conId.
        3. App reads the file, blurs it, paints it as the header
           backdrop.
      Cost: IPC channel, capture scheduling, cache invalidation.
      Substantial but genuinely new capability — the shell
      becoming a "glass server" for apps. Users notice this.
      Estimated: 2-3 sessions.

  [ ] "The Pool" — fluid desktop icons (V2 chosen)
      Sound assets (pool_bubble.wav, pool_pop.wav) already in
      assets/sounds/ — intended to fire on icon displacement
      (bubble) and settle (pop). NOT wired yet. VM has no working
      audio output; test on ISO after build.
      User's own invention. Desktop icons behave like water: when
      a widget card moves into a group of icons, they part and
      slide around it, staying nearby. Same for folders and any
      other desktop item.

      CHOSEN: V2 — Push + relax, with random re-settle.
        Widget moves → icons in its path are displaced to a nearby
        free grid cell. When the widget leaves, displaced icons
        do NOT spring back to their original position. Instead
        they settle into the nearest free space — like water
        molecules filling a container after a hand passes through.
        Over time the desktop drifts toward a new equilibrium
        each time a widget is dragged.

      WHY THIS OVER STRICT-RETURN:
        Returning icons to their exact original cell reads as
        "foam bouncing back" rather than water. Real water
        settles wherever there is space. This is the sharper
        reading of the metaphor.

      SETTING — "Foam" or "Water" (user picks one, no slider):
        Two discrete modes with descriptions in Settings:

        WATER:
          "Icons flow around widgets and settle wherever there
           is space. Like dropping a hand into a pool — the
           water parts and reforms around it. The arrangement
           evolves as you use the desktop."

        FOAM:
          "Icons bounce out of the way and return to their
           original places once the widget moves on. Predictable
           and tidy. Like foam held under a glass — let go and
           it springs back."

        Default: WATER. The invention is the water behaviour;
        foam is the escape hatch for users who want stability.

      PERSISTENCE:
        Arrangement is NOT saved to disk. Every shell restart
        begins with the user's original grid. Displacement is a
        transient, in-session behaviour — like water going still
        overnight.

      IMPLEMENTATION (V2, one session):
        - Each DesktopIcon remembers its "home cell" (grid slot)
          and current "settled cell".
        - On widget move (16 Hz while dragging), check each icon
          against every WidgetCard rect. If overlap, displace to
          nearest free cell weighted by the "gravity" slider.
        - On widget release, run a 5 Hz relax tick for ~2 s:
          icons gently drift toward lerp(home, settled, gravity).
        - Every displacement never overwrites the original home
          cell — so gravity=100 always restores the pristine grid.
        - Collision grid: 96x108 per icon at default, sized to
          the desktop canvas.

      VISUAL FEEL:
        - Icons drift at ~180 px/s while displaced.
        - Slight overshoot and settle on the relax tick (not
          bouncy, just a soft landing).
        - No rotation, no scaling — pure position.

  [ ] "The Pool" — V3 full fluid (backlog)
      Force-field version. Icons become velocity-based particles
      with mutual repulsion, widget attraction, and (optionally)
      spring-to-home. Integrated every 16 ms.

      Pros: smoothest possible water feel. Genuinely alive.
      Cons: hard to tune. Prone to oscillation, clumping,
            jitter. Requires a physics pass and a UI to tune
            stiffness/damping/mutual-force.

      Ship only if V2 feels too stiff after real use. Not before.

  [ ] "The Pool" — V4 physical shake (V3+/V2 backlog, "500/50")
      The wild variant. Desktop icons react to physical motion
      of the machine itself. Tilt the laptop → icons slide to
      the low edge, bouncing off walls. Shake the machine →
      they scatter and collide. When it settles flat again,
      icons land wherever they naturally stopped — a new
      arrangement each time, not the original.

      "500/50" — user's words. Meaning: five-hundred-percent
      effort, fifty-percent confidence. Worth logging even if
      it never ships.

      What it needs:
        - Real accelerometer / gyroscope input. VM has neither.
          Only works on actual laptop hardware with sensors.
        - Linux: /sys/bus/iio/devices/iio:device*/ with
          in_accel_*_raw files (Intel Sensor Hub, HP/Lenovo
          sensors, Apple SMC). Not on most desktops.
        - Physics engine: gravity vector from accel, friction on
          floor, elastic collisions with walls + other icons +
          widget obstacles. Same integrator as V3 but driven by
          an external force instead of user drag.
        - Continuous 60 Hz integration while any accel is
          non-zero.
        - Icons must be able to rotate for full effect (a tilted
          laptop means tilted gravity, icons at angles look
          wrong if they stay upright) — this doubles the
          complexity.

      Fallback: a "Shake" button in Settings that injects a
      synthetic accel impulse on demand, for VMs and desktops
      without sensors. Testable, still fun.

      Estimated: 2-3 sessions minimum. Ship only after V2 has
      had weeks of real use.

  [ ] Widget toggle — persistence across restarts
      Top bar Ω → View → Toggle Desktop Widgets hides or shows
      every floating card. Works in-session but does not persist:
      the toggle mutates cfg.widgetsVisible in memory only.

      Why in-memory only: VisualConfigManager::save() re-reads the
      config from disk before writing, which overwrites our
      in-memory change with the stale on-disk value. The config
      watcher then fires on mtime change and re-shows the cards —
      the "flash" bug that made the toggle useless.

      Fix to try later (one of):
        A) Fix save() to write m_cfg as-is without reloading.
           Would also fix other settings that might have the same
           race. Risky — save() may re-read for a reason (merging
           external edits). Audit before touching.
        B) Add a separate savePath() that skips the reload, use it
           only for the toggle. Small, safe, one-off.
        C) Write directly to visual.json in the toggle (mirroring
           how Settings::setAndSave works). Duplicates a little
           logic but is self-contained.

      Recommendation: B. Small, safe, no risk to the rest of the
      config system. One small session.

  [~] SUGGESTION — Auto-themes from wallpapers
      Idea (from CUSTOMISATION_VISION.md Elaboration 3): when the
      wallpaper changes, extract its dominant colours and recolour
      the whole shell to match.

      STATUS: deferred indefinitely at the user's request
      (2026-10-16). Reason logged so a future AI does not
      re-propose it without context.

      WHY IT WAS DECLINED:
        - ThemeManager::neutralize() (theme.h ~line 78) strips all
          colour from any theme passed to it. This is a deliberate
          design rule, not an oversight: "nothing in the UI carries
          colour except traffic lights and app icons." Auto-themes
          would have to delete or bypass that rule.
        - Sigil::* accessors in style.h (~lines 220-232) return
          hardcoded QColor values. Widgets call those, not
          ThemeManager::current(). Even a successfully extracted
          theme would change nothing on screen without rewriting
          every Sigil accessor and re-testing every call site.
        - The 7 curated seals (style.h ~line 230) are the
          sanctioned source of accent colour. Their rule is
          "warm, muted, earth-bound. No neon, no default blue."
          Auto-extraction from photographs produces saturated
          colours and would contradict that rule.
        - Livery (2026-10-16) added a third colour axis: per-app
          border accent. A fourth (wallpaper-driven) would create
          competing colour systems with no priority order.
        - Every one of the 8 wallpaper subclasses already overrides
          theme() with a hand-tuned Theme. Auto-extraction would
          make those dead code.

      WHAT STILL COULD WORK (if ever revisited):
        - Variant 2 from the 2026-10-16 discussion: an eighth seal
          called "Wild" that pulls ONE accent colour from the
          wallpaper. Everything else stays graphite/bone/oxblood.
          Smallest possible breach of the aesthetic.
        - Variant 1: a suggestion toast that maps the wallpaper to
          the closest of the existing 7 seals. Non-destructive.

      DECISION: do not build. The shell's identity is graphite,
      bone, and one accent chosen from 7 curated seals. That is
      the product. Auto-themes is a Windows/Rainmeter-class
      feature that fights the design language.

  [~] SUGGESTION — The Pool V2: windows as obstacles
      Exploratory. Not scheduled. Logged in case it's wanted.

      Idea: open windows (Finder, Notes, etc.) also push desktop
      icons aside, the same way widget cards do. Icons would flow
      around any window on screen, not just floating widgets.

      How it would work:
        - Reuse the existing 30 Hz swaymsg poll that drives the
          wallpaper parallax. Feed every window rect from
          `swaymsg -t get_tree` into the Pool's obstacle list,
          alongside the widget cards.
        - No new infrastructure — the poll already runs, the
          collision code already exists. Just a second source of
          obstacle rects.
        - Icons would reflow when you open, close, move, or
          resize any window.

      Why it might be wanted:
        - Natural extension of the invention.
        - Makes the desktop feel alive to window activity.

      Why it might not:
        - Busy. Icons rearrange every time you open Finder, drag
          a window, focus a different app.
        - Nobody does this. macOS, Windows, KDE — none. So no
          reference for whether it feels right.
        - Could interact badly with the parallax feature — both
          features would want the same window data.

      Decision: build only if the base Pool feels right after
      a week of real use AND the busy-ness tradeoff is acceptable.
      Otherwise close this line.
