MULTI-WINDOW MODEL (design 2026-10-17 — build starts next session)
------------------------------------------------------------------------
Decision (user, 2026-10-17): N processes per app, one window each —
Model A, Windows-style (two File Explorers with independent state,
transfer between them). NOT one-process-many-windows. Replaces the
old single-instance requirement in MANDATORY APP CHECKLIST.

Why: matches the user's actual workflow (two Finder windows pointing
at different disks, transferring between them). Windows/macOS-style.
Single-instance was a Linux-era constraint the shell inherited; it
does not fit the "macOS look, Windows compatibility" mission.

BEHAVIOUR MATRIX — every click path

  Action             App state        Result
  -----------------  ---------------  -------------------------------
  Dock single-click  not running      Launch (1 process, 1 window)
  Dock single-click  minimized        Restore + focus
  Dock single-click  focused          Minimize (Win 11 toggle)
  Dock single-click  running bg       Focus (bring to front)
  Pool icon click    not running      Launch (1 process, 1 window)
  Pool icon click    running (any)    Spawn NEW process (fresh window,
                                      independent state — the point)
  Dock middle-click  running          Quit App (kill ALL processes)
  Dock right-click   running          Menu: Close Window / Quit App /
                                             Remove from Dock
  Dock right-click   not running      Menu: Open App / Remove from Dock

No separate double-click handler: Win 11 taskbar is single-click
toggle, so implementing single-click correctly covers it. A double-
click is just two toggles; harmless.

OPEN QUESTIONS — resolve during pilot, not before
  1. Running dot with N processes: dot lit if ANY process with
     matching app_id exists (Windows taskbar behavior). Verify.
  2. Close Window targeting: right-click "Close Window" needs the
     focused process — swaymsg [app_id=X] kill targets the focused
     con. Middle-click needs to kill ALL: swaymsg [app_id=X] kill
     on every con, or kill -TERM every tracked PID.
  3. Settings double-instance bug: currently spawns a second Settings
     when clicking twice, because matchId = "apokolips-shell" catches
     Settings AND Finder AND the shell itself. Fix falls out of the
     rewrite (no more matchId focus probe on launch path).
  4. HUD focus tracking: g_trackedConId points at one window; with N
     windows, need the focused leaf. Existing focus poll already
     handles this — verify.

BUILD PLAN — one app per session
  S1  Notes (has tabs already; smallest surface) — remove IPC
      probe, fix running dot, add Close Window + Quit App menu
      entries, verify matrix
  S2  Finder
  S3  Calculator + myMach + BoomTube
  S4  Aperture + Node + Settings
  S5  Pool icon click path (always spawn new on desktop click)
  S6  Middle-click across all apps (Quit App)

Total 5-6 sessions. NOT a fast win. Picked because it's coherent,
user-facing, and matches the actual workflow.

The pre-Model-A middle-click patch (Variant A, chrome.h, held
2026-10-17) is SUPERSEDED — do not apply it. Under Model A, middle-
click must kill ALL processes for the app, not one.

OUT OF SCOPE, do not resume without user naming (Rule #2):
  - Model B (one process, N windows)
  - Model C (every click spawns a new window, even from dock)

  GitHub: lytone-lab/APOKOLIPS-OS

      While a window is fullscreen, moving the pointer to the

      (True macOS fullscreen green-button already shipped
      2026-10-14 — this V2 entry is only the auto-hide-reveal

  [ ] Window glass V2 — real glass (real backdrop, not wallpaper)
      Currently the app header strip shows a *blurred wallpaper*
      behind the traffic lights. Real macOS glass blurs what is
      actually behind the window — other windows, desktop icons,
      the dock. On Wayland apps cannot read pixels behind them
      directly, so the only path is:
        1. Shell captures the screen (grim) around the window's
           rect when the window moves, resizes, or a window
           beneath it changes.
        2. Shell writes the cropped region to a shared file or
           socket keyed by the app's sway conId.
        3. App reads the file, blurs it, paints it as the header
           backdrop.
      Cost: IPC channel, capture scheduling, cache invalidation.
      Substantial but genuinely new capability — the shell
      becoming a "glass server" for apps. Users notice this.
      Estimated: 2-3 sessions.

  [ ] Dock window previews on hover
      Hover a dock icon with multiple windows open → thumbnail
      popup above the dock showing each window's actual content.
      Click a thumbnail to focus that window.

      Behaviour (Windows 11 / Aero-Peek flavoured):
        - Hover the dock icon → small preview panel slides up
        - Each open window of that app becomes a card with:
            * a live thumbnail (grim -g <window rect>)
            * the window title truncated to 40 chars
            * a close button (X) per window
        - Move off the dock icon → panel slides away
        - Click a thumbnail → swaymsg focus that con, panel closes

      Implementation notes:
        - Poll or listen: `swaymsg -t get_tree` for windows per
          app_id. The shell already does this for the running dot.
        - Screenshot each window: `grim -g "x,y wxh" /tmp/prev.png`
          Throttle to 1 Hz, or on demand when the hover opens.
        - Widget: new class DockPreviewPopup, child of the shell
          root, positioned above the dock icon. Same visual
          language as the notification cards (glassy, rounded).
        - Auto-timeout the preview after 5s idle.

      Estimated: 1 session.

  [ ] "The Pool" — fluid desktop icons (V2 chosen)
      Sound assets (pool_bubble.wav, pool_pop.wav) already in
      assets/sounds/ — intended to fire on icon displacement
      (bubble) and settle (pop). NOT wired yet. VM has no working
      audio output; test on ISO after build.
      User's own invention. Desktop icons behave like water: when
      a widget card moves into a group of icons, they part and
      slide around it, staying nearby. Same for folders and any
      other desktop item.

      CHOSEN: V2 — Push + relax, with random re-settle.
        Widget moves → icons in its path are displaced to a nearby
        free grid cell. When the widget leaves, displaced icons
        do NOT spring back to their original position. Instead
        they settle into the nearest free space — like water
        molecules filling a container after a hand passes through.
        Over time the desktop drifts toward a new equilibrium
        each time a widget is dragged.

      WHY THIS OVER STRICT-RETURN:
        Returning icons to their exact original cell reads as
        "foam bouncing back" rather than water. Real water
        settles wherever there is space. This is the sharper
        reading of the metaphor.

      SETTING — "Foam" or "Water" (user picks one, no slider):
        Two discrete modes with descriptions in Settings:

        WATER:
          "Icons flow around widgets and settle wherever there
           is space. Like dropping a hand into a pool — the
           water parts and reforms around it. The arrangement
           evolves as you use the desktop."

        FOAM:
          "Icons bounce out of the way and return to their
           original places once the widget moves on. Predictable
           and tidy. Like foam held under a glass — let go and
           it springs back."

        Default: WATER. The invention is the water behaviour;
        foam is the escape hatch for users who want stability.

      PERSISTENCE:
        Arrangement is NOT saved to disk. Every shell restart
        begins with the user's original grid. Displacement is a
        transient, in-session behaviour — like water going still
        overnight.

      IMPLEMENTATION (V2, one session):
        - Each DesktopIcon remembers its "home cell" (grid slot)
          and current "settled cell".
        - On widget move (16 Hz while dragging), check each icon
          against every WidgetCard rect. If overlap, displace to
          nearest free cell weighted by the "gravity" slider.
        - On widget release, run a 5 Hz relax tick for ~2 s:
          icons gently drift toward lerp(home, settled, gravity).
        - Every displacement never overwrites the original home
          cell — so gravity=100 always restores the pristine grid.
        - Collision grid: 96x108 per icon at default, sized to
          the desktop canvas.

      VISUAL FEEL:
        - Icons drift at ~180 px/s while displaced.
        - Slight overshoot and settle on the relax tick (not
          bouncy, just a soft landing).
        - No rotation, no scaling — pure position.

  [ ] "The Pool" — V3 full fluid (backlog)
      Force-field version. Icons become velocity-based particles
      with mutual repulsion, widget attraction, and (optionally)
      spring-to-home. Integrated every 16 ms.

      Pros: smoothest possible water feel. Genuinely alive.
      Cons: hard to tune. Prone to oscillation, clumping,
            jitter. Requires a physics pass and a UI to tune
            stiffness/damping/mutual-force.

      Ship only if V2 feels too stiff after real use. Not before.

  [ ] "The Pool" — V4 physical shake (V3+/V2 backlog, "500/50")
      The wild variant. Desktop icons react to physical motion
      of the machine itself. Tilt the laptop → icons slide to
      the low edge, bouncing off walls. Shake the machine →
      they scatter and collide. When it settles flat again,
      icons land wherever they naturally stopped — a new
      arrangement each time, not the original.

      "500/50" — user's words. Meaning: five-hundred-percent
      effort, fifty-percent confidence. Worth logging even if
      it never ships.

      What it needs:
        - Real accelerometer / gyroscope input. VM has neither.
          Only works on actual laptop hardware with sensors.
        - Linux: /sys/bus/iio/devices/iio:device*/ with
          in_accel_*_raw files (Intel Sensor Hub, HP/Lenovo
          sensors, Apple SMC). Not on most desktops.
        - Physics engine: gravity vector from accel, friction on
          floor, elastic collisions with walls + other icons +
          widget obstacles. Same integrator as V3 but driven by
          an external force instead of user drag.
        - Continuous 60 Hz integration while any accel is
          non-zero.
        - Icons must be able to rotate for full effect (a tilted
          laptop means tilted gravity, icons at angles look
          wrong if they stay upright) — this doubles the
          complexity.

      Fallback: a "Shake" button in Settings that injects a
      synthetic accel impulse on demand, for VMs and desktops
      without sensors. Testable, still fun.

      Estimated: 2-3 sessions minimum. Ship only after V2 has
      had weeks of real use.

  [ ] Widget toggle — persistence across restarts
      Top bar Ω → View → Toggle Desktop Widgets hides or shows
      every floating card. Works in-session but does not persist:
      the toggle mutates cfg.widgetsVisible in memory only.

      Why in-memory only: VisualConfigManager::save() re-reads the
      config from disk before writing, which overwrites our

      the "flash" bug that made the toggle useless.

        A) Fix save() to write m_cfg as-is without reloading.
           Would also fix other settings that might have the same
           race. Risky — save() may re-read for a reason (merging
           external edits). Audit before touching.
        B) Add a separate savePath() that skips the reload, use it
           only for the toggle. Small, safe, one-off.

           how Settings::setAndSave works). Duplicates a little
           logic but is self-contained.

      Recommendation: B. Small, safe, no risk to the rest of the
      config system. One small session.

  [~] SUGGESTION — Auto-themes from wallpapers
      Idea (from CUSTOMISATION_VISION.md Elaboration 3): when the
      wallpaper changes, extract its dominant colours and recolour
      the whole shell to match.

      STATUS: deferred indefinitely at the user's request
      (2026-10-16). Reason logged so a future AI does not

      WHY IT WAS DECLINED:
        - ThemeManager::neutralize() (theme.h ~line 78) strips all
          colour from any theme passed to it. This is a deliberate
          design rule, not an oversight: "nothing in the UI carries
          colour except traffic lights and app icons." Auto-themes
          would have to delete or bypass that rule.
        - Sigil::* accessors in style.h (~lines 220-232) return
          hardcoded QColor values. Widgets call those, not
          ThemeManager::current(). Even a successfully extracted
          theme would change nothing on screen without rewriting
          every Sigil accessor and re-testing every call site.
        - The 7 curated seals (style.h ~line 230) are the
          sanctioned source of accent colour. Their rule is
          "warm, muted, earth-bound. No neon, no default blue."
          Auto-extraction from photographs produces saturated
          colours and would contradict that rule.
        - Livery (2026-10-16) added a third colour axis: per-app
          border accent. A fourth (wallpaper-driven) would create
          competing colour systems with no priority order.
        - Every one of the 8 wallpaper subclasses already overrides
          theme() with a hand-tuned Theme. Auto-extraction would
          make those dead code.

          wallpaper. Everything else stays graphite/bone/oxblood.
          Smallest possible breach of the aesthetic.

          the closest of the existing 7 seals. Non-destructive.

      bone, and one accent chosen from 7 curated seals. That is
      the product. Auto-themes is a Windows/Rainmeter-class
      feature that fights the design language.

      Idea: open windows (Finder, Notes, etc.) also push desktop
      icons aside, the same way widget cards do. Icons would flow
      around any window on screen, not just floating widgets.

      How it would work:

      Otherwise close this line.

  1. [OPEN — diagnosed 2026-10-17, not fixed] Per-app HUD: three bugs

     Reported as one. Verified as three. User: "the per-app menu reverts
     back when tried to hover on it, yet window still open. All buttons
     don't work." Priority: fix 1a first — until the HUD is stable under
     the mouse, 1b/1c can't be tested reliably.

     1a — HUD reverts to "Apokolips" on hover (BLOCKER)
       Repro: focus Finder/Notes/etc → HUD shows app-specific colour +
       buttons → move pointer onto the top bar → HUD snaps back to
       "Apokolips" while the app window is still open and focused.

       Root cause hypothesis (NOT yet verified in the running shell —
       verify before patching):
         Hovering the top bar makes sway report the SHELL as focused
         (top bar is a shell-owned surface). The focus poller in
         main.cpp (~2011-2290) sees id == "apokolips-shell" with no
         "Settings" title, so it falls into the hover-guard branch
         (~line 2158):
             bool overTopBar = topBar->isMouseOver();
             if (overTopBar && !g_trackedAppId.isEmpty())
                 effectiveId = g_trackedAppId;
             else { g_trackedAppId.clear(); effectiveId.clear(); }
         topBar->isMouseOver() reads m_hovered on the TopBar widget.
         The HUD is a SIBLING widget (main.cpp ~1998, added to
         topLayout separately), not a child of TopBar. When the pointer
         moves onto the HUD it leaves the TopBar's rect → m_hovered
         flips false → guard fails → g_trackedAppId is cleared →
         effectiveId empties → falls through to the "else" branch that
         calls topBar->setBrandColor(QColor()) and hud->setVisible(false).

       Fix shape (when scheduled):
         Extend the guard so it stays true over the whole top strip,
         not just the TopBar child. Options:
           (i)  also check `hud->underMouse()` in the guard
           (ii) compare QCursor::pos().y() against the top strip's
                global rect (top bar + HUD share one horizontal band)
         Either is ~3 lines. Pick one variant when scheduled per
         TEAM_PROTOCOL "propose 3 variants" (or state why one correct
         path is right — this is a bug fix, not a feature).

     1b — Window cycling buttons (< / >) inconsistent
       Report: "most apps have 1 instance, moving from different windows
       may not work." cycleApp (main.cpp ~2190) walks sway's get_tree
       for con_ids matching app_id and focuses the next one. With 1
       window the cycle is a no-op (expected). Open question: does it
       actually move between two windows of the same app, or does it
       get stuck? Cannot test until 5a is fixed (HUD disappears before
       the button can be clicked).

     1c — HUD action buttons have zero click wiring
       Verified by grep 2026-10-17: no `hudClicked`, `onHud`,
       `makeHudButton`, or `QPushButton::clicked` connection to the
       HUD exists anywhere in chrome.h or main.cpp. `setHud(...)`
       receives a `QList<QPair<QString, std::function<void()>>>` of
       action lambdas, but the HUD widget (chrome.h:2005 HUDWidget,
       paintEvent only) draws labels and never emits a click signal.
       The visible `menuButtons` are hidden (`b->setVisible(false)`)
       whenever setHud fires. So the lambdas are captured and never
       invoked.
       Fix shape: either (i) give HUDWidget real QPushButtons laid
       out inside it, wired to the action lambdas, or (ii) add hit-
       testing to HUDWidget::mousePressEvent that maps the click
       position to an action index and invokes the lambda. Option (i)
       is the simpler/cleaner route and matches the top-bar menu style
       already used elsewhere.

     Do NOT split this into three separate bug-list entries until 1a
     is fixed. Keeping them together preserves the causal chain
     (1a blocks testing 1b, 1c is independent). Once 1a is fixed and
     1b/1c can be retested visually, they may each graduate to their
     own entry — or close, if the symptom was entirely caused by 1a
     blocking access to the buttons.

  4. [OPEN — new 2026-10-17, not fixed] Genie timing races
     User report 2026-10-17 (verbatim): "sometimes the animation
     finishes when window already opened, sometimes window first
     flashes before animation plays."

     Two symptoms, likely related to the minimize/restore handshake:
       (a) Restore (reverse genie): animation completes AFTER the
           real window has already appeared — the overlay plays over
           the real window or trails behind it.
       (b) Minimize (forward genie): the real window is briefly
           visible for a frame or more BEFORE the overlay covers it.

     AI_HANDOFF.md §5 documents the intended sequence: the shell must
     hide the real window ONLY on the overlay's ready-sock ping (which
     fires from overlay's first paintEvent + 25 ms). If the ping ever
     fires early or is missed, symptom (b) appears. Reverse direction
     is the mirror problem.

     Root cause NOT yet diagnosed. This is intermittent — user reports
     "sometimes," so it is a race, not a systematic bug. Candidates
     when scheduled:
       - ready-sock timing relative to overlay's actual first paint
         (overlay boot ~200 ms in VM, variable under load)
       - scratchpad show/restore sequence for reverse (does the real
         window get shown before the overlay's final frame?)
       - daemon vs fresh-process spawn for the two directions
         (minimize goes through daemon, restore spawns fresh — ~200 ms
         difference documented in AI_HANDOFF §4)

     Do NOT attempt a fix without a fresh diagnostic. Reproducing a
     race requires a stress test (minimize/restore N times, count
     failures) or timing instrumentation in the overlay. V1 ship is
     not blocked by this — it is intermittent and cosmetic.
